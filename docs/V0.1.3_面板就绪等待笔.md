## 1. 诊断结论（改动依据，已实证勿再试）

2026-10-15 两轮 Console 诊断（fss 日常 Chrome、面板打开状态）：

1. **scrollTop 赋值有效**：对滚动容器 `comments--xxx`（可滚的那个）赋值 ST 0→600 生效，页面无 wheel 拦截。
2. **滚到底触发下一批**：`scrollTop = scrollHeight` 跳底后 2 秒，卡片 22→**42**，容器 SH 6476→**12880**。批大小 ≈ 20 张 ≈ 6400px 高。fss 手动滚动同样观察到新评论陆续冒出——**无限滚动加载机制确认，无分页按钮**。
3. **页面上有两个 `comments--` 容器**：预览区的（SH=CH=638 不可滚）和面板的（SH=6476 CH=669 可滚）。现有 tick 的"不可滚 continue"已正确跳过前者。
4. **根因 = 收工早于面板渲染**：点扩展 → `clickSeeAllComments` → 首批 20 张渲染，链路数秒；而 `NO_NEW_ROUNDS_GIVEUP=3` 的判定约 7 秒即触发 `no-more` 收工。收工时面板卡片尚未入 DOM，scan 只扫到预览区 2 条。

## 2. 改动（全部在 inject_main.js）

### 2.1 常量区两处

```js
  var NO_NEW_ROUNDS_GIVEUP = 6;       // 连续 6 轮无新评论（批间加载实测 ~2s，3 轮容错不够）
  var SCROLL_STEP_RATIO = 1.2;        // 每轮滚 1.2 倍容器视口高（20 张/批 ≈ 6400px，步长加大提速；跳底反而不取，仍需逐步）
```

（`COLLECT_MAX_REVIEWS=300`、`COLLECT_MAX_SECONDS=240` 不动——超时收割语义已有，收到多少算多少。）

### 2.2 startCollection：tick 启动前加"面板就绪门"

把末尾 `setTimeout(tick, 800);` 一行替换为：

```js
    // 面板就绪门：等首批卡片渲染出来（或容器可滚）才开始收集计时，
    // 否则 3~6 轮放弃判定会跑赢面板加载，收工时只扫到预览区
    var waitForPanel = function (tries) {
      var ready = document.querySelectorAll(CARD_SELECTOR).length > 0;
      if (!ready) {
        try {
          var cs = document.querySelectorAll(SCROLL_CONTAINER_SEL);
          for (var i = 0; i < cs.length; i++) {
            if (cs[i].scrollHeight > cs[i].clientHeight) { ready = true; break; }
          }
        } catch (e) { /* 忽略 */ }
      }
      if (ready) {
        st.startAt = Date.now(); // 计时从就绪起算，等待期不占用 240s 预算
        setTimeout(tick, 400);
      } else if (tries > 0) {
        setTimeout(function () { waitForPanel(tries - 1); }, 500); // 每 0.5s 复查，最多 15s
      } else {
        setTimeout(tick, 200); // 等不到（无面板场景）也开跑，走预览区/启发式原有流程
      }
    };
    waitForPanel(30);
```

注意：`waitForPanel` 引用了 `tick`（函数表达式赋给 var，定义在后）——`waitForPanel(30)` 的首次调用发生在 `tick` 赋值之后（同步代码自上而下执行完才进异步回调），无 TDZ 问题，顺序不要颠倒即可。
